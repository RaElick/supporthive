# Архитектура SupportHive

```
 Telegram ──► telegram_bot.py ─┐
                               ├─► services/tickets.py ──► SQLite/PostgreSQL (SQLAlchemy)
 Виджет (React) ──► /api/widget┘          │
                                          ▼
                                agents/pipeline.py  (асинхронные задачи)
                                 ├─ triage.py    тема, приоритет, краткое описание
                                 ├─ router.py    выбор оператора (стратегии)
                                 ├─ copilot.py   черновик ответа оператору
                                 └─ quality.py   оценка закрытого диалога
                                          │
                                 events.py (WebSocket-хаб) ──► панель оператора / виджет
 Дашборд (React) ──► /api/admin/* ──► services/metrics.py
```

## Слои

| Слой | Где | Правило |
|---|---|---|
| Домен и хранение | `app/models.py`, `app/db.py` | Ничего не знает про LLM и HTTP |
| Сервисы | `app/services/` | Вся бизнес-логика; вызываются из API и бота |
| Агенты | `app/agents/` | Зависят от сервисов только через переданные данные; не пишут в БД сами — возвращают результат, его сохраняет `pipeline.py` |
| API | `app/api/` | Тонкий слой: валидация, авторизация, вызов сервиса |
| Фронт | `frontend/` | Общается только с `/api` и `/ws` |

## Агентский контур (собственный харнес)

- `agents/llm.py` — клиент OpenAI-совместимого Chat Completions API (httpx), JSON-ответы
  с валидацией по Pydantic-схеме и повтором при ошибке. Если `LLM_BASE_URL` не задан —
  `llm = None`, и каждый агент использует детерминированную эвристику. Система всегда работает.
- `agents/context.py` — `ContextBuilder`: фрагменты контекста с приоритетом и бюджетом
  токенов. Низкоприоритетные фрагменты вытесняются (заменяются пометкой) при превышении бюджета.
  Порядок размещения (`system_first` / `recency_last`) настраивается — это точка для экспериментов.
- Каждое решение агента логируется (`AgentRun`): агент, режим (llm/heuristic), вход, выход,
  длительность. Решения маршрутизатора дополнительно — в `RoutingDecision`.

## Стратегии маршрутизации

| Стратегия | Суть |
|---|---|
| `queue` | общая очередь: свободный оператор с наименьшей загрузкой, FIFO |
| `skills` | балл = совпадение навыка с темой + история успешных решений по теме − загрузка |
| `llm` | LLM выбирает из отфильтрованных кандидатов, ответ проверяется по списку; при ошибке — `skills` |

Активная стратегия задаётся в настройках администратором (`/api/admin/settings`).
`app/simulate.py` прогоняет синтетическую нагрузку по всем стратегиям и сравнивает метрики.

## Жизненный цикл обращения

`new` → (triage) → `queued` → (router) → `assigned` → `closed` → (оценка клиента, quality review)

Если свободных операторов нет, обращение остаётся `queued`; при освобождении оператора
(закрытие заявки или выход онлайн) очередь перераспределяется.
